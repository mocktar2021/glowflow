# GLOW-9 invitation delivery contract (inactive)

Migration `20261104004728` was applied only to the GlowFlow Supabase project after a separately approved preflight. Its encrypted outbox is empty. The code includes a hidden owner request page, accessible FR/EN/ES invitation content, a provider-neutral one-at-a-time delivery function, and an inactive Resend adapter. The adapter does **not** send email until a separately activated worker invokes it. No worker or cron job, sending domain, API key, or hosted setting is configured here. The feature flags default to off. GLOW-9 remains in progress until provider setup, activation, and signed-in owner/recipient acceptance are verified.

## Boundaries

- `enqueue_staff_invitation_delivery` is callable only by the service role. The server wrapper gets the current Auth user, requires a confirmed address, and passes that user ID to the RPC. PostgreSQL rechecks that the ID is the verified owner of exactly the chosen tenant. No browser token or tenant ID selects a tenant.
- PostgreSQL serializes requests against the tenant row. A stable request UUID is idempotent. A different request for a recipient with an open delivery returns the same delivery ID without producing another token. Limits are three queued attempts per recipient per salon per hour and 20 per owner per day, counting failed sends too.
- The 43-character invitation token is returned only to a future trusted sender through a service-role claim. The invitation table holds only its SHA-256 digest. The private outbox holds AES-256 ciphertext and has RLS with no direct application-role table grants. The encryption passphrase is a server secret and must not appear in logs or browser bundles.
- A previous usable invitation is not revoked merely because a replacement was queued. A definite provider failure invalidates only the unsent replacement. A confirmed provider acknowledgement revokes prior unaccepted links for the same recipient and salon. An unknown provider result stays `uncertain` for manual reconciliation; it must not be blindly resent.
- A future transport must use the claim's stable idempotency key with a provider that supports idempotent send semantics, classify acknowledgements carefully, then call `settle_staff_invitation_delivery`. A two-minute claim lease and bounded retry count prevent a hot loop, but cannot alone prove whether a timed-out provider call delivered. The current provider-neutral function never sends a second claim attempt and treats a definite first-attempt non-send as failed, not retryable. This conservative policy avoids a duplicate if lease expiry follows a lost acknowledgement, but an operator must separately reissue a failed invitation. An uncertain outcome needs manual reconciliation.
- The hidden owner page is checked twice: the authenticated owner membership must match the salon, then PostgreSQL independently rechecks verified Auth identity and owner relationship before enqueue. The page is unavailable unless recipient acceptance, issuance, and delivery flags are all on. **Do not turn those flags on now:** there is no verified sending domain, worker, or monitoring.
- The template is intentionally tri-lingual because the current outbox claim does not persist a recipient language. All three URLs keep the 43-character token in a fragment, not a request path or query. Any future provider must disable click tracking/link rewriting that strips fragments.
- Invitation links use the explicit server-side `GLOWFLOW_APP_URL`, never a hardcoded production fallback. It must be an HTTPS origin under `glowflow.mocktar.com` or `glowflow.beauty` (including a dedicated subdomain), without a path, query, fragment, credentials, or non-default port. A Vercel Preview must use a dedicated subdomain, not either apex app host. If the origin is missing or invalid, the sender does not claim an outbox item. Confirm the chosen host and Auth redirect allowlist for each environment before enabling delivery; this code change does not create a QA environment or switch the production domain.
- The inactive Resend adapter requires a server-only key, a sender on `email.glowflow.mocktar.com`, and a monitored reply-to address. It sends HTML and text with the claim's stable `Idempotency-Key` header. A known rejected request is a definite non-send; a timeout, rate limit, server error, or malformed acknowledgement is uncertain. It neither logs provider payloads nor retries. Do not configure a key or sender before choosing the correct Resend account and verifying the domain.

## Activation checklist (separate work)

1. Choose the correct Resend account and verify `email.glowflow.mocktar.com` as a sending-only domain on existing free capacity. Review SPF, DKIM, DMARC, monitored reply-to, suppression, retention, and privacy. Keep click tracking off because link rewriting may strip token fragments.
2. Review the server-only adapter and build a worker/schedule outside the owner request response. The worker must guard the three feature flags and provider configuration, alert on failed settlement and uncertain outcomes, and never blindly retry an unknown send.
3. Set `GLOWFLOW_INVITE_OUTBOX_KEY` only in the server environment. Coordinate recipient acceptance, issuance, and delivery flags; do not enable any of them until the worker and provider are ready. A missing or weak key makes issuance and delivery fail closed.
4. Verify live owner-only enqueue and recipient acceptance with a controlled test account, including wrong salon, expired link, confirmed email mismatch, resend, and provider failure. Do not use a customer address for the first send.
5. If issuance must be halted, apply the narrowly scoped rollback to revoke the three delivery RPC grants. It retains outbox and invitation audit rows; it does not delete data. Separately disable the flags and worker.

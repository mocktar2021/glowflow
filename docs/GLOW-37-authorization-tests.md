# GLOW-37 authorization regression coverage

The `Database security / RLS and role authorization` pull-request job fails if source guards or real PostgreSQL authorization tests fail. It starts PostgreSQL 16 and creates a uniquely named disposable database for each run; an absent admin URL, invalid target, missing client, failed migration, skipped database setup, or failed test makes the job fail. The generated database is dropped in `finally`, including after subprocess timeout. No Supabase credentials or deployed data are used.

Run source checks with `node --test tests/rls-source-guards.test.mjs`. Run the database checks with `GLOWFLOW_RLS_ADMIN_DATABASE_URL` set to a loopback PostgreSQL URL whose database is `postgres`, then `node tests/rls-run.mjs`. Set `PSQL_BIN` when `psql` is not on PATH. Use a disposable local cluster: the dependency fixture creates the `anon`, `authenticated`, and `service_role` cluster roles if absent. Do not point this at a shared or production cluster.

The runner creates a separate empty database for each of two suites:

1. `schema-database.test.mjs` loads a minimal Supabase platform substitute (Auth, Storage, roles and Realtime publication), the restored historical baseline, then every migration in timestamp order. Application tables, policies, grants, triggers and functions are the real checked-in SQL. It checks runtime RLS enablement on every public table and exercises owner, staff, anonymous, unaffiliated and cross-tenant access to clients, users, services, appointments and invoices. It includes permitted client CRUD, forbidden tenant reassignment and role escalation, owner-only catalog edits and invoice deletion restrictions.
2. The existing sandbox suite applies the actual sandbox connections and reservation migrations over a minimal synthetic dependency fixture. It verifies owner-only reads, cross-tenant invisibility, forbidden browser-role writes, hidden event data, service-only RPC permissions and empty RPC search paths, alongside concurrent booking, idempotency and reconciliation checks.

`supabase/schema.sql` is the last intact pre-migration baseline from commit `7eb3950`; it is deliberately not a generated current-schema snapshot. Fresh installations must apply all migrations after it. This repairs duplicated/malformed snapshot content without rewriting deployed migration history. Do not run the baseline or indiscriminately replay migrations against a shared database.

A source check examines all checked-in public table declarations for RLS enablement and rejects later disablement. Unqualified table declarations and table drops fail closed until the guard is explicitly extended for that migration. A separate client import graph check follows local alias and relative imports, re-exports and literal dynamic imports/require calls into the privileged Supabase helper. Explicit `use server` modules are server-action boundaries; Next.js also enforces the helper's `server-only` import during the production build. Regression fixtures demonstrate that violations fail the guards. These source checks are deliberately conservative and are not a general TypeScript or SQL parser.

## Remaining acceptance work

Full-schema creation and core role checks do not establish exhaustive operation coverage for every tenant table. Expand the role matrix to scheduling, queue, public-profile and Storage policies, including public-field allowlists, before closing GLOW-37. Platform substitutes do not validate Supabase JWT verification, hosted API grants, uploads or Realtime delivery. Shared-project migration history still needs reconciliation; a clean local replay is not a production backup/restore exercise. Making the job a required merge check is a branch-protection setting, not changed here. While GitHub minutes are exhausted, the owner has requested the same checks run locally; report local runtime differences explicitly.

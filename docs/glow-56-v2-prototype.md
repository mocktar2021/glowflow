# GLOW-56 v2 booking recovery prototype (not enabled)

This code is a draft, stacked on the GLOW-56 mounted-page safeguard. `GLOWFLOW_PUBLIC_BOOKING_V2_ENABLED` defaults off. With the gate off, the existing booking route and UI remain active; v2 returns 404. With the gate on, the legacy arbitrary-request-key POST returns 410 before any database call, and the booking page uses the v2 intent flow. **Do not enable the gate in a hosted environment yet.** The draft private-intent migration, reviewed retention policy, scheduled expiry/scrub/purge, and operational rollout are separate prerequisites. No hosted database change is included here.

The single `POST /api/public-booking/v2` endpoint accepts exactly one of `bootstrap`, `prepare`, `reconcile`, `commit`, `cancel`, or `acknowledge`. Every action requires an exact same-origin `Origin`, same-origin Fetch Metadata if present, strict JSON shape, and bounded body. It sends only a SHA-256 hash of a random browser token to the five service-role-only RPCs. A new browser token is held in a host-only `__Host-glowflow_booking_session` cookie with `Secure`, `HttpOnly`, `SameSite=Strict`, and `Path=/`. `GLOWFLOW_PUBLIC_BOOKING_V2_COOKIE_MAX_AGE_SECONDS` has no default and must be a validated, separately approved server-only setting before a token can be issued. The cookie lifetime is not itself a PII retention policy.

If the Max-Age setting is later removed, issuing a new cookie and every fresh `prepare` fail closed; an existing valid cookie can still bootstrap and reconcile/commit/cancel/acknowledge its original intent so configuration rollback does not strand an ambiguous booking. This is recovery-only behavior, not permission for a new booking.

The separate draft `GLOWFLOW_PUBLIC_BOOKING_V2_RECOVERY_ONLY=true` mode closes v1 with the same 410, blocks new cookie issuance and `prepare`, and denies no-ID reconcile before its RPC because the present SQL can create a browser session there. An exact signed-cookie intent can still reconcile, commit, cancel, or acknowledge. This is not an activation-ready operational rollback: if both v2 flags disappear after a cutover, the app defaults to OFF and v1 POST reopens. The application cannot infer a past cutover from missing environment configuration. A reviewed durable database cutover/freeze guard and owner-approved operations procedure must prevent that downgrade before any hosted activation; never use OFF as a post-cutover recovery setting.

The server's browser+salon generation is returned by a no-ID reconcile and passed as `expected_generation` to prepare. The database must atomically reject stale generations and serialize prepare, commit, cancel, expiry, and acknowledge as specified in GLOW-56 design PR #179 and database draft PR #180. A terminal result for an exact old intent cannot authorize a fresh prepare; the UI always obtains the current generation again. A confirmed intent can be released for a new booking only by explicit acknowledgement, followed by current reconcile. No 400/409, missing row, or ambiguous response alone unlocks a changed booking.

Before commit, the UI writes `glowflow.booking.pending.<public-salon-slug>.<intent-uuid>=1` to localStorage. The UUID is not a bearer capability without the independent HttpOnly cookie. The marker contains no contact details, requested slot, request key, or cookie. Failed marker write blocks commit. Reload/new-tab recovery reconciles every marker by exact ID; an unknown marker or marker with a lost cookie requires manual salon contact. A delayed old-tab result can remove only its own marker. Clearing *all* site data erases both cookie and marker and is undetectable, so that remains an explicit limitation. Browser fixtures simulate API outcomes; they do not prove database locking races, which belong to the real PostgreSQL suite in PR #180.

V2 confirmation enriches only the RPC-bound appointment after a matching tenant, appointment ID, and start-time read. It uses the associated current service price/currency, published salon name/address/policies, and validated tenant time zone. The service title stays the immutable booked snapshot from the intent RPC, not a mutable catalog title. Any mismatch or read error leaves `details: null` without changing the authoritative confirmed result. Focused API and FR/EN/ES browser fixtures cover this fallback, but hosted integration and operations review are still required.

Activation blockers: the private-intent migration is unmerged/unapplied, its retention policy is intentionally unseeded, and scheduled expiry/scrub/purge has not been approved or implemented. SameSite=Strict, cookie expiry and legacy-client cutover also need browser/operations review. Keep draft PRs and the flag off until those gates are resolved.

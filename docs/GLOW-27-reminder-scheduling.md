# GLOW-27: consented email schedule persistence

This slice records confirmation and future 24-hour and 2-hour reminder jobs in the existing append-only outbox. It does not send a message, install a worker or cron job, call a provider, or charge anything. The scheduler migration is present on hosted GlowFlow as of 2026-11-03. It enables outbox persistence, not message delivery.

## Behavior

The `public.appointments` trigger runs in the same transaction as insertion or a real start-time/status revision. A confirmed appointment with a nonblank client email and a latest explicit `email:consented` event gets a confirmation entry and any reminder entries whose scheduled times are still in the future. A canceled appointment, unknown consent, opt-out, or missing email creates no new entries. A later consent event does not retroactively schedule a prior booking; a subsequent appointment revision can schedule it. SMS and WhatsApp are not automatic channels.

The existing generation bump invalidates pending entries when start time or status changes. History is preserved for audit. The request key is the UUID form of `md5('glowflow:g27:email:' || appointment_id || ':' || generation)` and is stable across retries. The pre-existing service-role `schedule_appointment_notifications` RPC remains available, but manual callers replaying an automatically scheduled revision must use this key. The RPC intentionally rejects a different key for the same revision. The trigger does not change its semantics or silently replace its entries.

The trigger is an internal `SECURITY DEFINER` function with an empty search path, table/operation guard, and no direct execute grant for public, anonymous, authenticated, or service roles. The existing appointment mutation path remains the authorization boundary. Existing outbox row-level security and delivery-eligibility checks remain in force.

## Pending delivery-claim hardening

The read model treats a pending reminder as superseded when its stored appointment start differs from the appointment's current start, even if the schedule generation did not change. The existing `private.notification_delivery_eligible(uuid, timestamptz)` function does not make that comparison. A privileged start-time correction or a missed generation bump could therefore leave a new claim eligible while the read model says superseded. The normal trigger's generation bump reduces this risk but is not a substitute for a fail-closed claim gate. In addition, `public.claim_notification_delivery(uuid, uuid, timestamptz)` returns an existing same-key claim before rechecking eligibility. A replay could return a claim ID after its appointment was moved. No sender or claim worker is active in this repository; this is a pre-activation defect, not evidence that a stale reminder was sent.

The repair must be a **new CLI-generated, versioned migration** that hardens both new-claim eligibility and same-key replay, preserving function signatures, security properties, direct grants, and all unrelated conditions. A replay should be idempotent only while the original claim remains current, unexpired, and without a recorded result, and while the appointment and consent remain eligible; it must not insert another attempt. Fresh-claim due checks should use database time rather than the caller's permitted five-minute-ahead timestamp. Do not edit applied migration `20261101172437` or mark a future migration applied without executing its exact reviewed SQL. A code merge alone does not apply SQL to Supabase. Pair the migration with disposable-PostgreSQL tests for a due reminder, an early timestamp, a changed start with unchanged generation, a valid in-lease same-key replay, and replay after a mismatch, expiration, or recorded result. Keep provider delivery, cron, telemetry, and paid flows disabled throughout this repair. Locking the outbox alone does not lock the appointment against a later change; an eventual worker still must recheck appointment state and effective consent immediately before external send.
